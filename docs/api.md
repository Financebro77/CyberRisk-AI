# API

CyberRisk AI ships a **FastAPI** backend. The API wraps the existing,
already-tested tool functions **read-only** — no route computes numbers; every
figure comes from the engine.

> **Status.** The API is the current integration surface (used by the React
> frontend and available for programmatic access). The sections below document
> the routes as they exist today, and describe the planned future API surface
> (auth, SDK, versioning). Interactive docs are auto-generated by FastAPI at
> `http://localhost:8000/docs` when the server is running.

---

## 1. Getting started

```bash
pip install -e ".[web]"
python -m uvicorn cyberrisk.api.main:app --port 8000
```

- Base URL: `http://localhost:8000`
- Interactive docs (Swagger): `http://localhost:8000/docs`
- Health check: `GET /api/health`

The API also serves the built React frontend on `/` in production mode.

---

## 2. Conventions

- **All request/response bodies are JSON.**
- **All fields are optional unless noted.** The engine works on partial
  briefs and reports what it assumed — or returns a **completeness guard**:
  `{"status": "insufficient_info", "needed": [...]}` telling the client which
  facts are required before modelling (revenue + security controls).
- **Numbers are never invented.** Routes call the same tools the AI agent
  calls; responses are engine outputs.

### The client brief

Most POST routes accept a `CompanyBrief`-shaped body:

```json
{
  "firm_name": "MedData Health Technologies",
  "industry": "Healthcare",
  "revenue_usd": 400000000,
  "customer_records": 10000000,
  "technology_dependency": "High",
  "security_controls": "partial MFA, weekly backups, onboarding-only vendor assessment",
  "previous_incidents": 0,
  "existing_coverage": "$5M limit, $500k retention",
  "risk_appetite": "retain up to $1.5M"
}
```

## 3. Endpoints

### 3.1 Health

**`GET /api/health`**

Liveness check.

```json
{ "status": "ok", "service": "CyberRisk AI", "version": "0.1.0" }
```

### 3.2 Score a company

**`POST /api/score`**

Body: a client brief. Returns the 0–100 score, risk category, domain scores,
and risk drivers. Deterministic — the same brief always yields the same score.

```bash
curl -X POST http://localhost:8000/api/score \
  -H "Content-Type: application/json" \
  -d '{"firm_name":"Acme","industry":"Manufacturing","revenue_usd":500000000,"security_controls":"partial MFA"}'
```

```json
{
  "firm_name": "Acme",
  "risk_score": 62.4,
  "risk_category": "High",
  "risk_drivers": ["external_attack_surface", "patch_cadence"],
  "domain_scores": { "...": 0 }
}
```

### 3.3 Run the loss model

**`POST /api/simulate`**

Body: a client brief + optional `n_years` (1,000–500,000; default 100,000).
Returns EAL, VaR 95/99, ES 95/99, PMLs, the loss distribution, and
per-scenario contribution. Requires `revenue_usd` + `security_controls` —
otherwise returns the completeness guard.

```json
{
  "status": "ok",
  "eal": 3620000,
  "var_95": 13370000,
  "var_99": 27420000,
  "es_99": 42710000,
  "pml_1in200": 0,
  "pml_1in1000": 0,
  "loss_distribution": { "...": 0 },
  "prob_zero_loss": 0.102,
  "scenario_contribution": { "ransomware": 0.31 }
}
```

### 3.4 Analyse an insurance structure

**`POST /api/insurance`**

Body: a client brief + optional policy terms. Returns the ground-up loss, the
insurer's response (covered loss, insurer payment, probability the annual
limit is exhausted), and the client's **retained residual exposure** at the
P99.9 tail.

Policy terms (all optional):

```json
{
  "per_occurrence_deductible": 250000,
  "per_occurrence_limit": 5000000,
  "annual_aggregate_deductible": 1000000,
  "annual_aggregate_limit": 20000000,
  "coinsurance": 0
}
```

### 3.5 Optimise an insurance structure

**`POST /api/insurance/optimise`**

Runs the requested policy through the insurance analysis, then sweeps a grid
of limit × retention combinations over the **same cached simulation** and
recommends the structure that best closes the residual-exposure gap per dollar
of additional limit.

```json
{
  "status": "ok",
  "current": { "...": "the tested structure's analysis" },
  "recommended": {
    "policy_limit": 20000000,
    "retention": 500000,
    "residual_exposure": 0,
    "insurer_payment": 0,
    "p_annual_limit_exhausted": 0,
    "evaluation": "..."
  },
  "ground_up_loss": { "...": 0 }
}
```

### 3.6 Model a control improvement

**`POST /api/controls-improvement`**

Body: a client brief + a required `control_change` (e.g. *"implement MFA"*).
Returns before/after EAL, VaR 99, ES 99, and the loss reduction %.

### 3.7 Generate the Excel report

**`POST /api/report`** — writes the assessment workbook, returns its path.

**`GET /api/report/download`** — streams the most recently generated workbook
as a file download.

### 3.8 Executive report

**`POST /api/report/executive`**

Aggregates score + simulation + insurance + scenario contribution into a
single response that the Executive Report page renders. Every figure comes
from the engine.

### 3.9 Model methodology

**`GET /api/model/methodology`**

Returns the white-box methodology sections (scoring, frequency/severity
adjustments, simulation) — the same text the UI shows on the Methodology page.

### 3.10 Scenario catalog

**`GET /api/scenarios`**

Returns the calibrated scenario catalog: key, name, frequency model, annual
rate λ, severity model.

### 3.11 Chat sessions (AI consultant)

The chat API is stateful — the backend owns the `CyberRiskAgent` (and its
memory / client facts) per session.

| Route | Purpose |
|---|---|
| `POST /api/chat/sessions` | Create a session → returns `session_id` |
| `POST /api/chat/{session_id}/turns` | Send a message → returns the answer + `tool_trace` |
| `DELETE /api/chat/{session_id}` | End a session |
| `GET /api/chat/sessions/{session_id}/history` | Get UI-safe history |

The `tool_trace` in each turn lists the tools actually executed and their
results — the UI renders charts **only** from these, never from invented
numbers. Chat requires a configured LLM provider (`LLM_PROVIDER` + key);
without one, session creation returns a 503.

## 4. Future API surface

The API is evolving toward a production integration surface. Planned (in
priority order):

- **API-key authentication** — `Authorization: Bearer <key>` for machine
  clients, with per-key rate limits (LLM calls are billed).
- **Versioning** — a stable `v1` prefix (`/api/v1/...`) once the surface
  freezes; the current routes stay as the unversioned fast path.
- **OpenAPI SDK** — generated typed clients (Python / TypeScript) from the
  OpenAPI schema, so integrations don't hand-roll HTTP.
- **Batch / async** — `POST /api/jobs` for long simulations (portfolio runs),
  returning a job id polled via `GET /api/jobs/{id}`.
- **Portfolio endpoints** — aggregate exposure across a book of clients
  (correlated loss), the current research focus.
